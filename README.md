# 回页｜技术路线

> 目标：用最少、可解释、可演进的技术，支撑“有出处的主动回望”。

## 1. 当前技术主线

不推倒现有前端，继续使用：

- **TypeScript + React + Vinext：** 当前页面与交互的基础；
- **Cloudflare Workers / Sites：** 承载服务端接口与私密 MVP 部署；
- **D1：** 日记、版本、权限、标签、对话和反馈等结构化数据；
- **R2：** 图片与未来的大附件；
- **D1 FTS5：** 关键词全文检索；
- **向量索引（后接 Vectorize）：** 找到“措辞不同、意思相近”的记录；
- **模型适配层：** 服务端调用模型，不把密钥放在前端；首选 Responses API，并保留更换模型供应商的能力。

第一版是私密、单用户 MVP，不要为了多账号和复杂权限体系拖慢核心闭环。

## 2. 数据分层

AI 日记的核心不是模型，而是数据边界。每一层都必须可追溯、可删除。

| 数据层 | 保存什么 | 是否可被 AI 静默改写 |
|---|---|---|
| 原文记录 | 用户输入的正文、来源、时间、附件 | 不可以 |
| 用户编辑版本 | 用户自己修改后的内容 | 不可以 |
| AI 整理建议 | 标题、标签、摘要、未闭合问题 | 可以重生成，但不覆盖原文 |
| 检索片段 | 被允许关联内容的切片、关键词、向量、权限元数据 | 关闭关联或删除时失效 |
| 对话与引用 | 用户问题、回答、当次引用了哪些原文 | 可查看、可删除 |
| 长期记忆（后续） | 用户明确确认过的理解 | 只能由用户确认后写入 |

## 3. 写入与整理流程

```text
用户保存原文
  → 记录权限：是否整理 / 是否允许关联
  → 原文、版本、附件保存
  → 如允许整理：模型返回结构化建议
  → 用户接受、编辑或保留原文
  → 如允许关联：为可用版本建立检索片段与索引
```

AI 整理使用固定 JSON 结构，而不是自由散文。第一版字段保持很少：`title`、`tags`、`summary`、`open_questions`。

## 4. 主动回望：最小 RAG 流程

```text
用户提出问题
  → 仅筛选允许关联的记录
  → 关键词检索（精确词、书名、人名）
  + 语义检索（含义相近、措辞不同）
  → 时间 / 来源 / 权限过滤
  → 排序与最低相关度阈值
  → 取 2～3 篇原文作为证据
  → 模型回答，并输出引用及关联理由
  → 用户给召回质量反馈
```

第一版不需要复杂 Agent。它本质上是一个受权限约束的检索工具，加上一段证据驱动的对话生成。

## 5. 为什么不用“把所有日记喂给 AI”

那样在记录变多后成本高、答案不稳定，也无法保证关闭关联或删除后内容真的不被使用。

RAG 的职责是“在当前问题发生时，临时找回少量可能相关的过去”，而不是代替长期记忆。

## 6. 关键实现难度

| 模块 | 难度 | 真正难点 |
|---|---:|---|
| 日记增删改查、导出 | 2/5 | 可靠、不丢数据 |
| 附件与来源 | 2/5 | 存储、迁移与导出 |
| AI 整理 | 2.5/5 | 输出稳定、不篡改原意 |
| 权限与删除链路 | 3/5 | 派生摘要、向量、索引同步失效 |
| 带来源主动回望 | 4/5 | 准确、克制、可解释 |
| 思考回环 | 4/5 | 不把牵强关联说成用户变化 |
| 被动 hint | 5/5 | 少而准，且不打扰 |

## 7. 评估先于“更聪明”

每次主动回望都记录：

- 提问；
- 实际引用的日记；
- 用户反馈：相关 / 牵强 / 无关 / 有启发；
- 是否点回原文；
- 是否应该减少、增加或换掉引用。

这会形成回页自己的评估集。后续优化优先调整检索、过滤和阈值，而不是盲目更换模型。

## 8. 8 月 MVP 的技术实现顺序

1. 整理现有前端状态与数据结构；
2. 加入可靠草稿、版本、权限与导出；
3. 设计 D1/R2 数据模型，完成私密数据保存；
4. 接入服务端 AI 整理，要求结构化输出；
5. 建立关键词检索与权限过滤；
6. 加入向量检索、少量证据引用与对话；
7. 建立真实问题评估集，依据反馈调召回质量。

## 9. 后续再学习与实现

按产品需求学习即可：数据模型 → API → 数据库 → 结构化输出 → Embedding → RAG → Evals → 确认式记忆。

在有真实记录和真实问题之前，不优先学习复杂 Agent 框架、知识图谱或微调。
