# 回页｜技术路线

## 当前目标

回页不是通用聊天机器人。当前技术目标是跑通一个可解释的回响闭环：保存时静默建立候选关联；回响页一次交还一篇有原文证据的旧思考；用户反馈决定它以后如何出现。

## 当前架构

```text
React / TypeScript 前端
  ├─ 日记、草稿、设置、回响反馈：当前设备的 localStorage
  ├─ 写作、日记池、详情、Markdown、导出
  └─ 调用 Worker API

Cloudflare Worker
  ├─ /api/organize：可选 AI 整理，固定 JSON 输出
  └─ /api/recall：从候选旧记录中严格判断是否值得带回

OpenRouter 模型
  ├─ 整理：标题、最小整理稿、标签
  └─ 回响：是否召回、旧记录 ID、原文引句、轻量理由
```

密钥只在服务端环境变量中使用。日记原文当前仍保存在用户设备；只有用户允许关联的记录会在发起关联判断时发送给模型。

## 回响 0.1 流程

```text
保存新记录
  → 过滤：仅允许关联的旧记录
  → 候选：当前 MVP 传入少量已有记录
  → AI 严格判断：无确实价值则不返回
  → 校验：引用必须是候选原文中的精确片段
  → 本地保存 Echo（pending / opened / continued / irrelevant）
  → 回响页最多展示一张 pending 卡片
```

回响 API 不是“相似文本搜索”。模型必须判断旧记录是否提供背景、旧假设、反例、条件或未完成问题；仅关键词相同必须拒绝。

## 数据模型

### Entry

- `content`：当前可读版本；
- `originalContent`：不可被 AI 覆盖的原文；
- `createdAt`、来源、附件；
- `aiLink`：是否允许未来关联；
- `continuesFrom`：用户沿着哪篇旧记录继续写。

### Echo

- 当前记录与旧记录 ID；
- 可核对的旧原文引句；
- 限长的关联理由；
- 状态：`pending`、`opened`、`continued`、`irrelevant`；
- 生成时间。

## 为什么还不是完整 RAG

当前版本只服务于少量真实日记的体验验证，不需要先引入复杂基础设施。随着记录数量增长，再引入：

- D1：日记、版本、权限、思考线、回响反馈；
- R2：图片和附件；
- FTS：精确检索；
- Vectorize / Embedding：从大量记录中生成候选；
- rerank / recall gate：决定候选是否真的值得展示。

向量检索负责“找得到”；回响判断负责“该不该出现”；用户反馈负责“以后如何出现”。三者不能混为一谈。

## 非目标

- 不做复杂 Agent 编排；
- 不把模型推断自动写成长期用户画像；
- 不把 AI 整理作为记忆系统的核心；
- 不以聊天回答替代用户自己的判断。

## 当前数据原则

- 每篇记录只有一份用户确认的「我的思考」；AI 整理不再是当前主线。
- 日记、草稿、回响反馈与设置默认仅保存在当前设备、当前浏览器。
- Markdown 导出只适合阅读备份；后续将补充 JSON 结构化导出与导入，完成换电脑迁移。
